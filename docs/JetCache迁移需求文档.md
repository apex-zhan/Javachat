## 1. 需求背景

### 1.1 现状问题

当前 MallChat 项目使用自研的 AbstractRedisStringCache 批量缓存框架，存在以下问题：

1. **性能瓶颈**
   - 所有缓存查询都需要访问 Redis
   - 热点数据响应时间 5-10ms
   - 高并发场景下 Redis 压力大

2. **维护成本高**
   - 需要维护自研框架代码（312行）
   - 每个缓存类需要实现 40 行代码
   - 缺少统计和监控功能

3. **功能不完善**
   - 不支持本地缓存
   - 缺少缓存穿透/击穿防护
   - 缺少缓存统计功能

### 1.2 业务影响

- 会话列表查询响应时间 150ms（目标 < 50ms）
- 群成员列表查询响应时间 200ms（目标 < 100ms）
- Redis QPS 过高，接近性能瓶颈

## 2. 需求目标

### 2.1 性能目标

| 指标 | 现状 | 目标 | 提升 |
|-----|------|------|------|
| 热点数据响应时间 | 5-10ms | <1ms | 10倍+ |
| 会话列表响应时间 | 150ms | <50ms | 3倍 |
| Redis 访问量 | 100% | 10-20% | 降低 80-90% |
| 缓存命中率 | 60-70% | >90% | 提升 30% |

### 2.2 代码质量目标

| 指标 | 现状 | 目标 | 改善 |
|-----|------|------|------|
| 框架代码量 | 312行 | 20行 | 减少 90% |
| 每个缓存实现 | 40行 | 10行 | 减少 75% |
| 维护成本 | 中 | 低 | 降低 80% |

### 2.3 功能目标

- ✅ 支持两级缓存（Caffeine + Redis）
- ✅ 自动防止缓存穿透
- ✅ 自动防止缓存击穿（SingleFlight）
- ✅ 内置统计和监控
- ✅ 支持注解式和编程式

## 3. 技术方案

### 3.1 方案选择

**选择：JetCache 多级缓存方案**

**理由**：
1. 阿里开源，成熟稳定
2. 支持两级缓存（Caffeine + Redis）
3. 功能完善，开箱即用
4. 代码简洁，维护成本低
5. 已有部分代码实现

### 3.2 架构设计

```
业务代码 → @Cached注解 → Caffeine(1分钟) → Redis(30分钟) → 数据库
         ↑
    SingleFlight（防击穿）
```

### 3.3 核心组件

1. **JetCacheConfig**：配置类（已完成）
2. **JetCacheUtils**：工具类（已完成）
3. **SingleFlight**：防击穿组件（已完成）
4. **缓存类**：UserInfoCache、RoomCache 等（待迁移）
