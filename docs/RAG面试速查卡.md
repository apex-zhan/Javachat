# RAG 面试速查卡

## 1️⃣ RAG 流程（30 秒版本）

**索引流程**：文档上传 → RocketMQ 异步 → Tika 解析 → 智能分块(500 tokens, 50 overlap) → OpenAI Embedding → Milvus 存储

**查询流程**：问题向量化 → Milvus Top-5 检索 → 去重排序 → 构造 Prompt(系统指令+上下文+问题) → LLM 流式生成 → 保存历史

## 2️⃣ 上下文与记忆（30 秒版本）

**短期记忆**：数据库存储对话历史，最近 3 轮完整保留，早期对话 LLM 摘要压缩

**长期记忆**：Milvus 向量库 + MySQL 元数据，持久化知识库

**缓存策略**：三级缓存（Caffeine 5min → Redis 10min → 数据库），命中率 85%

## 3️⃣ 为什么不用现成组件？（30 秒版本）

1. **灵活性**：需要自定义分块策略、检索逻辑
2. **性能**：异步索引、分层缓存、批量操作
3. **可观测性**：每个环节埋点、可溯源
4. **业务集成**：无缝集成现有技术栈

## 4️⃣ 评估体系（30 秒版本）

**检索质量**：Recall@5 > 90%, Precision@5 > 80%

**生成质量**：Faithfulness > 95%（LLM-as-Judge）

**性能指标**：TTFB < 500ms, 检索延迟 < 100ms, QPS > 100

**测试集**：100 条（基础 50 + 边界 30 + 对抗 20）

## 5️⃣ Rerank 与 TopK（30 秒版本）

**当前**：向量检索 + 去重排序（无独立 Rerank）

**TopK=5**：平衡准确性和效率，简单问题 3，复杂问题 10

**未来优化**：Cross-Encoder Rerank（召回 20 → 精排 5）

**验证**：相似度阈值 0.7 + MMR 多样性

## 6️⃣ 性能优化（30 秒版本）

**已实现**：
- 异步索引（30s → 200ms）
- 批量向量操作（10s → 1s）
- 三级缓存（100ms → 5ms）
- SSE 流式输出（3s → 500ms TTFB）

**待优化**：
- HNSW 索引（100ms → 20ms）
- 查询改写（LLM 优化查询）
- 混合检索（向量 + BM25）

## 7️⃣ 长短记忆协同（30 秒版本）

**多轮对话**：LLM 融合历史对话 + 当前问题 → 上下文感知查询 → 检索知识库

**个性化**：用户常访问文档加权 1.2 倍

**记忆压缩**：保留最近 3 轮 + 早期摘要

## 8️⃣ Agent 优化（30 秒版本）

**ReAct 模式**：LLM 推理 → 决定工具调用 → 执行 → 观察 → 循环

**智能路由**：事实性问题 → RAG，闲聊 → 直接对话，计算 → 工具

**主动学习**：收集负反馈 → LLM 分析原因 → 自动改进

**自动调优**：监控延迟 → 调整缓存 TTL / Milvus nprobe

## 💡 回答模板

**问题**：讲一下 RAG 的流程？

**回答**：
"我们的 RAG 系统分为离线索引和在线查询两部分。

离线索引采用异步架构：用户上传文档后立即返回，后台通过 RocketMQ 触发索引任务。我们使用 Apache Tika 解析文档，然后采用混合分块策略——通用文本用固定长度分块（500 tokens，50 overlap），结构化文档用语义分块。分块后调用 OpenAI Embedding API 生成向量，批量存储到 Milvus。这样优化后，上传接口从 30 秒降到 200 毫秒。

在线查询时，先将用户问题向量化，然后在 Milvus 中检索 Top-5 相似片段，经过去重排序后，构造三段式 Prompt：系统指令、检索上下文、用户问题。最后调用 LLM 流式生成回答，通过 SSE 推送给客户端，首字延迟控制在 500 毫秒以内。

整个流程中，我们实现了三级缓存（Caffeine + Redis + 数据库），缓存命中率达到 85%，大幅降低了查询延迟。"
