## 七、面试高频问题（STAR回答模板）

### 7.1 介绍一下多类型消息的实现方案

**【STAR完整回答】**

**S - Situation（背景）：**
> "在MallChat项目中，IM系统需要支持10+种消息类型：文本、图片、视频、语音、文件、表情、位置、系统消息等。传统if-else方案会导致代码冗长、难以维护，而且每次新增消息类型都需要修改核心代码，违反开闭原则。"

**T - Target（目标）：**
> "我的设计目标是：
> 1. 单表存储，避免表爆炸和JOIN查询
> 2. 符合开闭原则，新增类型无需修改核心代码
> 3. 代码复用性高，减少重复代码
> 4. 自动注册机制，降低开发成本"

**A - Action（方案）：**
> "我采用了**策略模式 + 工厂模式 + 模板方法模式**的组合方案：
> 
> **1. 数据库设计：单表+JSON**
> - message表：type字段区分消息类型
> - extra字段（JSON）：存储各类型特有属性
> 
> **2. 抽象Handler模板：**
> - AbstractMsgHandler<Req>：定义模板方法checkAndSaveMsg()
> - 子类实现：saveMsg()、showMsg()等抽象方法
> 
> **3. 工厂自动注册：**
> - 使用@PostConstruct，Handler启动时自动注册到工厂
> - 通过反射获取泛型类型，自动识别请求体类型
> 
> **4. 具体实现：**
> - TextMsgHandler：敏感词过滤、URL识别、@用户
> - ImgMsgHandler：保存图片宽高、URL
> - LocationMsgHandler：保存经纬度、地图快照"

**R - Result（结果）：**
> "最终实现了：
> - ✅ 核心代码从500+行降至50行（减少90%）
> - ✅ 新增消息类型只需5分钟，无需修改核心代码
> - ✅ 代码复用率80%+，可维护性显著提升
> - ✅ 支持10+种消息类型，扩展性强
> 
> **反思：**
> 如果重新设计，我会考虑引入插件化机制，支持运行时动态加载Handler，进一步提升扩展性。"

### 7.2 为什么不用分表存储不同类型的消息？

**【STAR完整回答】**

**S - Situation：**
> "在设计之初，我对比了两种方案：分表存储（message_text、message_img）和单表存储（message + type + extra）。"

**T - Target：**
> "我的选择标准是：
> 1. 查询效率（消息列表需要按时间排序）
> 2. 扩展性（新增类型的成本）
> 3. 维护成本（表数量、索引管理）"

**A - Action（对比分析）：**

| 维度 | 分表方案 | 单表+JSON方案 | 选择 |
|-----|---------|--------------|------|
| **查询性能** | 需要UNION ALL多表 | 单表查询 | ✅ 单表 |
| **扩展性** | 每次新增需要建表 | 只需加Handler | ✅ 单表 |
| **表数量** | 10+张表 | 1张表 | ✅ 单表 |
| **索引管理** | 复杂（每张表都要建索引） | 简单 | ✅ 单表 |
| **JOIN查询** | 复杂（跨表） | 不需要 | ✅ 单表 |
| **字段清晰** | 清晰 | 需要看extra | ❌ 分表略优 |

> "基于以上对比，我选择了**单表+JSON**方案。"

**R - Result：**
> "实践证明这个选择是正确的：
> - 消息列表查询性能稳定在20ms以内
> - 新增位置消息类型只用了5分钟
> - 单表维护成本低，索引优化简单
> 
> **唯一缺点：**
> extra字段不便于复杂查询（如：查找所有@了某人的消息）。但这种需求很少，可以通过搜索引擎（ES）解决。"

### 7.3 策略模式和模板方法模式有什么区别？

**【技术深度回答】**

| 维度 | 策略模式 | 模板方法模式 | 在项目中的应用 |
|-----|---------|-------------|--------------|
| **定义** | 定义算法族，可互相替换 | 定义算法骨架，子类实现细节 | 组合使用 |
| **关系** | 组合关系（has-a） | 继承关系（is-a） | Handler继承抽象类 |
| **目的** | 算法可替换 | 流程统一、细节可变 | 不同类型用不同Handler |
| **实现** | 接口+实现类 | 抽象类+具体类 | AbstractMsgHandler |
| **运行时选择** | ✅ 是（工厂选择） | ❌ 否（编译期确定） | 运行时根据type选择 |

**在MallChat中的结合：**

```java
// 1. 模板方法模式：定义流程
public abstract class AbstractMsgHandler<Req> {
    // 模板方法（流程固定）
    public Long checkAndSaveMsg() {
        checkMsg();    // 钩子方法
        saveMsg();     // 抽象方法
    }
}

// 2. 策略模式：不同策略（Handler）可替换
AbstractMsgHandler handler = MsgHandlerFactory.get(type);  // 运行时选择
handler.checkAndSaveMsg();  // 调用模板方法

// 3. 工厂模式：管理策略
public class MsgHandlerFactory {
    private static Map<Integer, AbstractMsgHandler> map;
    public static AbstractMsgHandler get(Integer type);
}
```

### 7.4 如果要支持消息编辑功能，怎么设计？

**【开放性问题回答】**

**S - 需求分析：**
> "消息编辑功能需要考虑：
> 1. 编辑历史记录（追溯）
> 2. 已读用户的通知
> 3. 不同类型消息的编辑规则（文本可编辑，图片不可编辑）"

**T - 设计目标：**
> "1. 保留编辑历史，支持查看
> 2. 通知已读用户消息已编辑
> 3. 灵活控制哪些类型可编辑"

**A - 方案设计：**

**方案1：增加编辑标识+历史表**

```java
// 1. Message表增加字段
ALTER TABLE message ADD COLUMN `edit_count` INT DEFAULT 0 COMMENT '编辑次数';
ALTER TABLE message ADD COLUMN `last_edit_time` DATETIME COMMENT '最后编辑时间';

// 2. 创建编辑历史表
CREATE TABLE `message_edit_history` (
  `id` BIGINT AUTO_INCREMENT PRIMARY KEY,
  `msg_id` BIGINT NOT NULL COMMENT '消息ID',
  `old_content` TEXT COMMENT '原内容',
  `new_content` TEXT COMMENT '新内容',
  `edit_time` DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY `idx_msg_id` (`msg_id`)
) COMMENT='消息编辑历史';

// 3. Handler增加canEdit()方法
public abstract class AbstractMsgHandler<Req> {
    // 是否可编辑（子类重写）
    public boolean canEdit() {
        return false;  // 默认不可编辑
    }
    
    // 编辑消息
    public void editMsg(Message msg, Req newBody) {
        if (!canEdit()) {
            throw new BusinessException("该类型消息不支持编辑");
        }
        
        // 保存编辑历史
        saveEditHistory(msg);
        
        // 更新消息
        updateMsg(msg, newBody);
        
        // 通知已读用户
        notifyEditedUsers(msg);
    }
}

// 4. TextMsgHandler实现
@Component
public class TextMsgHandler extends AbstractMsgHandler<TextMsgReq> {
    @Override
    public boolean canEdit() {
        return true;  // 文本消息可编辑
    }
}
```

**R - 预期效果：**
> "- 编辑历史可追溯
> - 灵活控制编辑权限
> - 通知机制完善"

### 7.5 如何处理消息的多端同步？

**【系统设计问题】**

**S - 场景：**
> "用户在手机上发送消息后，PC端需要实时同步显示。"

**T - 目标：**
> "保证多端消息一致性，延迟<100ms。"

**A - 方案：**

```
┌──────────────────────────────────────────────┐
│            多端消息同步方案                    │
└──────────────────────────────────────────────┘

1. 手机端发送消息
   ↓
2. 服务器保存到数据库
   ↓
3. 发布消息事件
   ↓
4. MQ广播推送（RocketMQ BROADCASTING）
   ↓
5. 所有节点收到消息
   ↓
6. 推送到该用户的所有设备
   ├─ 手机WebSocket连接（节点A）
   └─ PC WebSocket连接（节点B）
```

**关键代码：**

```java
// 1. 记录用户的所有设备连接
public class WebSocketService {
    // key: uid, value: 该用户的所有Channel
    private static final Map<Long, CopyOnWriteArrayList<Channel>> USER_CHANNELS = new ConcurrentHashMap<>();
    
    public void addChannel(Long uid, Channel channel) {
        USER_CHANNELS.computeIfAbsent(uid, k -> new CopyOnWriteArrayList<>())
            .add(channel);
    }
    
    // 推送到用户的所有设备
    public void sendToAllDevices(Long uid, WSBaseResp msg) {
        List<Channel> channels = USER_CHANNELS.get(uid);
        if (CollectionUtil.isNotEmpty(channels)) {
            channels.forEach(channel -> sendMsg(channel, msg));
        }
    }
}

// 2. 消息推送时，推送给发送者+接收者的所有设备
public void pushMsg(Message msg) {
    List<Long> targetUids = new ArrayList<>();
    targetUids.add(msg.getFromUid());  // 发送者
    targetUids.addAll(getReceiverUids(msg));  // 接收者
    
    mqProducer.sendMsg(PUSH_TOPIC, new PushDTO(targetUids, msg));
}
```

**R - 效果：**
> "- 手机、PC、Pad等多端实时同步
> - 延迟<50ms
> - 支持离线设备上线后拉取"

## 八、设计模式深度对比

### 8.1 为什么不用观察者模式？

| 模式 | 优点 | 缺点 | 适用场景 |
|-----|------|------|---------|
| **策略模式（当前）** | 算法可替换、扩展性强 | 需要工厂管理 | 多种处理方式（消息类型） |
| **观察者模式** | 一对多通知、解耦 | 不适合替换算法 | 事件监听（消息发送事件） |

**结论：** 两者解决的问题不同，在项目中**组合使用**：
- 策略模式：处理不同类型的消息
- 观察者模式：消息发送后的事件通知（已在项目中使用Spring Events）

---

### 8.2 为什么不用责任链模式？

**假设用责任链：**

```java
// 校验链
public interface MsgCheckHandler {
    void check(Message msg);
    void setNext(MsgCheckHandler next);
}

// 使用
MsgCheckHandler chain = new BlacklistCheckHandler()
    .setNext(new FrequencyCheckHandler())
    .setNext(new PermissionCheckHandler());
chain.check(msg);
```

**对比：**

| 维度 | 策略模式 | 责任链模式 |
|-----|---------|-----------|
| **核心目的** | 选择算法 | 链式处理 |
| **职责** | 单一Handler处理完整流程 | 多个Handler处理部分逻辑 |
| **扩展性** | 新增类型加Handler | 新增校验加链节点 |
| **适用场景** | 完整业务处理 | 多步骤校验 |

**结论：**
- 消息保存：用**策略模式**（每种类型完整处理）
- 消息校验：可用**责任链模式**（黑名单→频控→权限）

---

### 8.3 如果用命令模式会怎样？

**命令模式实现：**

```java
public interface MsgCommand {
    void execute();
}

public class SendTextMsgCommand implements MsgCommand {
    private Message msg;
    private TextMsgReq body;
    
    @Override
    public void execute() {
        // 保存文本消息
    }
}

// 使用
MsgCommand command = new SendTextMsgCommand(msg, body);
command.execute();
```

**对比：**

| 维度 | 策略模式 | 命令模式 |
|-----|---------|---------|
| **核心目的** | 算法替换 | 封装请求 |
| **扩展性** | ✅ 易扩展 | ✅ 易扩展 |
| **撤销/重做** | ❌ 不支持 | ✅ 支持 |
| **异步执行** | ❌ 不支持 | ✅ 支持 |
| **适用场景** | 替换处理方式 | 请求队列、事务 |

**结论：**
如果需要**消息撤销/重做**功能，命令模式更合适。但当前需求只是不同类型处理，策略模式足够。

## 九、踩坑经验与解决方案

### 9.1 坑1：泛型擦除导致的类型转换错误

**问题现象：**

```java
@Component
public class TextMsgHandler extends AbstractMsgHandler<TextMsgReq> {
    // ...
}

// 调用时
handler.checkAndSaveMsg(request, uid);
// 错误：java.lang.ClassCastException: java.util.LinkedHashMap cannot be cast to TextMsgReq
```

**原因分析：**
前端传入的`request.body`是一个Map，Spring自动转换时没有类型信息。

**解决方案：**

```java
private Req toBean(Object body) {
    // 1. 如果已经是目标类型，直接返回
    if (bodyClass.isAssignableFrom(body.getClass())) {
        return (Req) body;
    }
    
    // 2. 使用BeanUtil转换（支持Map -> Bean）
    return BeanUtil.toBean(body, bodyClass);
}
```

**关键：** 通过反射获取泛型类型`bodyClass`，实现智能转换。

### 9.2 坑2：@PostConstruct注册时机问题

**问题现象：**

```java
// 启动时报错：NullPointerException
AbstractMsgHandler handler = MsgHandlerFactory.get(1);
```

**原因分析：**
Spring容器启动顺序不确定，可能Service先于Handler初始化，导致工厂为空。

**解决方案：**

```java
// 1. 延迟初始化（第一次使用时检查）
public static AbstractMsgHandler get(Integer type) {
    if (STRATEGY_MAP.isEmpty()) {
        // 触发Spring容器初始化所有Handler
        // （不推荐，应该在启动时完成）
    }
    return STRATEGY_MAP.get(type);
}

// 2. 使用ApplicationListener（推荐）
@Component
public class MsgHandlerInitListener implements ApplicationListener<ContextRefreshedEvent> {
    @Override
    public void onApplicationEvent(ContextRefreshedEvent event) {
        // 容器启动完成后校验
        if (MsgHandlerFactory.isEmpty()) {
            log.error("MsgHandler注册失败！");
        } else {
            log.info("MsgHandler注册成功，共{}个", MsgHandlerFactory.size());
        }
    }
}
```

### 9.3 坑3：JSON序列化时extra字段为null

**问题现象：**

```java
Message msg = messageDao.getById(1001);
System.out.println(msg.getExtra());  // null
```

**原因分析：**
MyBatis-Plus的JacksonTypeHandler需要配置`autoResultMap = true`。

**解决方案：**

```java
@TableName(value = "message", autoResultMap = true)  // ✅ 关键配置
public class Message {
    @TableField(value = "extra", typeHandler = JacksonTypeHandler.class)
    private MessageExtra extra;
}
```

**原理：**
- `autoResultMap = true`：自动配置ResultMap
- `typeHandler`：指定类型处理器

### 9.4 坑4：敏感词过滤导致消息内容错位

**问题现象：**

```java
// 原消息：你好@张三，请查看链接
// 过滤后：你好@***，请查看链接
// 问题：@用户的uid错位了
```

**原因分析：**
先存储@用户列表，后过滤敏感词，导致content变化但atUidList不变。

**解决方案：**

```java
// 1. 先过滤敏感词，再提取@用户
String filteredContent = sensitiveWordBs.filter(body.getContent());

// 2. 如果内容变化，重新解析@用户位置
if (!filteredContent.equals(body.getContent())) {
    // 标记atUidList需要前端重新解析
    extra.setNeedReparse(true);
}
```

或者：

```java
// 保存@用户的原始位置（offset）
extra.setAtUidList(body.getAtUidList());
extra.setAtOffsets([10, 15, 20]);  // 记录每个@的位置
```

// ✅ 批量获取消息
public List<ChatMessageResp> getMsgList(List<Long> msgIds) {
    // 1. 批量查询Message
    List<Message> messages = messageDao.listByIds(msgIds);
    
    // 2. 按type分组
    Map<Integer, List<Message>> typeMap = messages.stream()
        .collect(Collectors.groupingBy(Message::getType));
    
    // 3. 批量处理（减少Handler调用次数）
    List<ChatMessageResp> result = new ArrayList<>();
    typeMap.forEach((type, msgList) -> {
        AbstractMsgHandler handler = MsgHandlerFactory.get(type);
        msgList.forEach(msg -> {
            ChatMessageResp resp = buildResp(msg, handler);
            result.add(resp);
        });
    });
    
    return result;
}

// 定义插件接口
public interface MsgPlugin {
    void process(Message msg);
    int getOrder();  // 执行顺序
}

// 插件管理器
@Component
public class MsgPluginManager {
    @Autowired
    private List<MsgPlugin> plugins;
    
    @PostConstruct
    public void init() {
        // 按order排序
        plugins.sort(Comparator.comparing(MsgPlugin::getOrder));
    }
    
    public void processPlugins(Message msg) {
        plugins.forEach(plugin -> plugin.process(msg));
    }
}

// 使用
public class SensitiveWordPlugin implements MsgPlugin {
    @Override
    public void process(Message msg) {
        // 敏感词过滤
    }
    
    @Override
    public int getOrder() {
        return 1;  // 第一个执行
    }
}

## 十二、面试STAR卡片（速查）

### 卡片1：多类型消息方案

```
【S】IM系统需支持10+种消息类型，传统if-else难维护
【T】单表存储、符合开闭原则、代码复用80%+
【A】策略+工厂+模板方法：AbstractMsgHandler+具体Handler
【R】核心代码减少90%，新增类型5分钟，可维护性显著提升
```

### 卡片2：为什么不分表

```
【S】对比分表和单表+JSON方案
【T】查询效率、扩展性、维护成本
【A】单表+JSON：查询快、扩展易、索引简单
【R】查询<20ms，新增类型5分钟，单表维护成本低
```

### 卡片3：设计模式组合

```
【S】需要统一流程+不同处理+自动注册
【T】既要流程统一，又要算法可替换
【A】模板方法（流程）+策略（算法）+工厂（管理）
【R】代码复用80%，扩展性强，符合SOLID原则
```

### 卡片4：踩过的坑

```
【S】泛型擦除导致Map转Bean失败
【T】通过反射获取泛型类型，智能转换
【A】ParameterizedType获取泛型，BeanUtil转换
【R】解决类型转换问题，支持任意Req类型
```
