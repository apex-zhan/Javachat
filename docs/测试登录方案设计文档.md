## 一、问题背景

### 1.1 原始登录流程

MallChat 的登录采用微信公众号扫码授权模式，流程如下：

```
用户打开页面
  |
  v
前端 WebSocket 发送 RequestLoginQrCode（type=1）
  |
  v
后端调用微信接口生成临时二维码 URL
  |
  v
后端通过 WebSocket 返回二维码 URL（LoginQrCode type=1）
  |
  v
前端展示二维码，用户用微信扫码
  |
  v
微信服务器回调后端，后端推送 WaitingAuthorize（type=2）
  |
  v
用户在手机上点击确认登录
  |
  v
后端推送 LoginSuccess（type=3），包含 token + 用户信息
  |
  v
前端保存 token，建立 WebSocket 认证连接，进入聊天界面
```

### 1.2 本地开发的问题

| 问题点 | 说明 |
|--------|------|
| 需要微信公众号 | 必须注册真实的微信公众号，获取 appId + secret |
| 需要公网回调地址 | 微信回调后端接口必须是公网可访问的 URL，本地 `localhost` 无法接收回调 |
| 需要内网穿透 | 开发时必须使用 ngrok/cpolar 等工具做内网穿透 |
| 二维码生成失败 | `WxMpService.getQrcodeService().qrCodeCreateTmpTicket()` 在没有正确配置时会直接抛异常 |
| 前端永远 loading | 二维码请求失败，前端弹窗一直显示 `v-loading="!loginQrCode"`，用户无法继续 |

**结果**：本地开发环境下，前端登录弹窗只有遮罩层，无法进入系统，严重阻碍开发和调试。

## 二、方案总览

### 2.1 设计目标

1. **绕过微信登录**：本地开发时无需微信配置即可登录
2. **复用现有认证体系**：生成的 Token 与正式登录完全一致，走相同的认证流程
3. **最小侵入性**：不修改原有登录逻辑，仅新增一条旁路
4. **前端状态同步**：登录后前端所有状态（用户信息、WebSocket 连接）与正式登录一致
5. **生产环境安全**：测试接口不影响生产，可通过配置开关控制

### 2.2 方案架构

```
+-------------+      GET /public/testLogin/{uid}      +-------------+
|   前端页面   |  ----------------------------------->  |   后端 API   |
|  LoginBox   |                                      | UserController|
+-------------+                                      +-------------+
       |                                                   |
       | 返回 token                                        | loginService.login(uid)
       |<--------------------------------------------------|
       |                                                   |
       v                                                   v
+-------------+                                      +-------------+
| localStorage|                                      |   Redis     |
|  TOKEN      |                                      | USER_TOKEN  |
|  USER_INFO  |                                      +-------------+
+-------------+
       |
       v
+-------------+
|  WebSocket  |
| 重新初始化   |  <-- 带上 token 发起连接
+-------------+
```

## 五、核心原理分析

### 5.1 Token 生成机制

后端 `LoginService.login(Long uid)` 的实现逻辑：

```java
public String login(Long uid) {
    String key = RedisKey.getKey(RedisKey.USER_TOKEN_STRING, uid);
    String token = RedisUtils.getStr(key);
    if (StrUtil.isNotBlank(token)) {
        return token;  // 如果已存在有效 token，直接复用
    }
    // 生成新的 JWT token
    token = jwtUtils.createToken(uid);
    // 存入 Redis，5 天过期
    RedisUtils.set(key, token, 5, TimeUnit.DAYS);
    return token;
}
```

**关键点**：
- Token 使用 **JWT** 格式，包含 uid 信息
- Token 存储在 **Redis** 中，实现中心化管理和过期控制
- 同一 uid 多次登录会复用同一个 token（除非已过期）
- Token 有效期 5 天，剩余 1 天时自动续期

### 5.2 认证拦截流程

`TokenInterceptor.preHandle()` 的执行逻辑：

```java
public boolean preHandle(HttpServletRequest request, ...) {
    // 1. 从 Header 中提取 token
    String token = getToken(request);  // Authorization: Bearer xxx

    // 2. 校验 token 有效性
    Long validUid = loginService.getValidUid(token);

    if (validUid != null) {
        // 3a. token 有效：将 uid 放入 request 属性，供后续 Controller 使用
        request.setAttribute(ATTRIBUTE_UID, validUid);
    } else {
        // 3b. token 无效：检查是否是公开接口
        boolean isPublicURI = isPublicURI(request.getRequestURI());
        if (!isPublicURI) {
            // 非公开接口且未登录，返回 401
            HttpErrorEnum.ACCESS_DENIED.sendHttpError(response);
            return false;
        }
    }
    return true;
}
```

**公开接口判定规则**：URI 以 `/public/` 开头，如 `/capi/user/public/testLogin/10001`。

### 5.3 WebSocket 认证流程

WebSocket 连接建立时的认证：

```java
// NettyWebSocketServerHandler
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof WebSocketServerProtocolHandler.HandshakeComplete) {
        // WebSocket 握手完成后，检查 URL 参数中的 token
        String token = NettyUtil.getAttr(ctx.channel(), NettyUtil.TOKEN);
        if (StrUtil.isNotBlank(token)) {
            // 调用认证方法
            this.webSocketService.authorize(ctx.channel(), new WSAuthorize(token));
        }
    }
}
```

`WebSocketService.authorize()` 逻辑：

```java
public void authorize(Channel channel, WSAuthorize wsAuthorize) {
    boolean verifySuccess = loginService.verify(wsAuthorize.getToken());
    if (verifySuccess) {
        // token 有效：获取用户信息，发送 LoginSuccess 消息
        User user = userDao.getById(loginService.getValidUid(wsAuthorize.getToken()));
        loginSuccess(channel, user, wsAuthorize.getToken());
    } else {
        // token 无效：通知前端 token 失效
        sendMsg(channel, WSAdapter.buildInvalidateTokenResp());
    }
}
```

**核心洞察**：测试登录获取的 token 与微信登录获取的 token **完全一致**，都经过相同的 `loginService.login()` 方法生成，都走相同的 `loginService.verify()` 方法校验。因此 WebSocket 认证不需要任何改动。

### 5.4 前端状态同步

测试登录成功后，前端执行以下操作：

```typescript
// 1. 持久化登录凭证
localStorage.setItem('TOKEN', token);
localStorage.setItem('USER_INFO', JSON.stringify({ uid }));

// 2. 更新全局状态
userStore.isSign = true;           // 标记已登录
loginStore.showLogin = false;      // 关闭登录弹窗
loginStore.loginStatus = LoginStatus.Success;
loginStore.loginQrCode = undefined;

// 3. 重新初始化 WebSocket（带上新 token）
wsIns.initConnect();

// 4. 获取用户详情（头像、昵称等）
userStore.getUserDetailAction();
```

**状态对应关系**：

| 状态 | 微信登录 | 测试登录 | 说明 |
|------|---------|---------|------|
| `localStorage.TOKEN` | 有 | 有 | 两者一致 |
| `localStorage.USER_INFO` | 有（含完整信息） | 有（仅 uid） | 测试登录后通过 `getUserDetailAction()` 补全 |
| `userStore.isSign` | `true` | `true` | 标记登录态 |
| `loginStore.showLogin` | `false` | `false` | 关闭弹窗 |
| WebSocket 连接 | 已认证 | 已认证 | 都带 token |

## 六、为什么不用 Mock 数据

### 6.1 什么是 Mock 方案

Mock 方案通常指在前端代码中写死假数据，例如：

```typescript
// Mock 方案的伪代码
const mockLogin = () => {
  const fakeToken = 'fake_token_123';
  const fakeUser = { uid: 10001, name: 'MockUser', avatar: '...' };
  localStorage.setItem('TOKEN', fakeToken);
  userStore.userInfo = fakeUser;
  userStore.isSign = true;
};
```

### 6.2 Mock 方案的缺陷

| 缺陷 | 说明 |
|------|------|
| **Token 无效** | Mock 的 token 不是后端生成的 JWT，后端 `loginService.verify()` 会返回 false，所有需要认证的接口都会 401 |
| **WebSocket 无法认证** | WebSocket 连接时后端会校验 token，Mock token 会导致认证失败，无法收发消息 |
| **数据不同步** | Mock 的用户信息是写死的，与数据库实际数据不一致，可能导致奇怪的行为 |
| **需要改动后端** | 为了让 Mock token 通过校验，必须修改后端的 token 校验逻辑，这会污染生产代码 |
| **无法测试真实业务** | 发送消息、添加好友等操作都依赖后端认证，Mock 登录后这些功能都无法使用 |
| **维护成本高** | 每次后端改动（如 token 格式变化），Mock 数据都要同步更新 |

### 6.3 本方案 vs Mock 方案对比

| 维度 | Mock 方案 | 本方案（测试登录 API） |
|------|----------|----------------------|
| Token 真实性 | 假 token | 真实 JWT，后端生成 |
| 后端校验 | 需要改代码放行假 token | 不需要任何改动 |
| WebSocket 认证 | 无法通过 | 正常通过 |
| API 调用 | 部分接口 401 | 所有接口正常 |
| 数据一致性 | 假数据 | 与数据库一致 |
| 侵入性 | 高（前后端都要改） | 低（只新增接口和 UI） |
| 可维护性 | 差 | 好（与正式登录共用一套逻辑） |

### 6.4 设计原则

> **测试环境应该尽量接近生产环境，而不是绕过它。**

本方案的核心思想是：**让测试登录产生与真实登录完全相同的产物（Token）**，而不是伪造产物去骗过系统。这样测试环境的行为才具有参考价值。

## 七、为什么这样改 —— 逐文件说明

### 7.1 后端：UserController.java

**改动内容**：

```java
// 新增依赖注入
@Autowired
private LoginService loginService;

// 新增接口
@GetMapping("/public/testLogin/{uid}")
@ApiOperation("测试登录-直接获取token")
public ApiResult<String> testLogin(@PathVariable Long uid) {
    String token = loginService.login(uid);
    return ApiResult.success(token);
}
```

**为什么这样设计**：

| 设计决策 | 原因 |
|---------|------|
| 使用 `GET` 而非 `POST` | 操作简单，无副作用，符合 RESTful 语义 |
| 路径放在 `/public/` 下 | `TokenInterceptor.isPublicURI()` 判定规则是 URI 第 4 段为 `public` 时免登录。放在 `/public/` 下确保未登录用户也能调用 |
| 路径参数 `{uid}` 而非请求体 | 简单直观，方便直接在浏览器地址栏测试，如 `http://localhost:8080/capi/user/public/testLogin/10001` |
| 复用 `loginService.login()` | 保证生成的 Token 与正式登录完全一致，走相同的 JWT 生成 + Redis 存储逻辑 |
| 返回 `ApiResult<String>` | 与项目中其他接口的返回格式保持一致，前端无需额外处理 |
| 不使用配置开关 | 本接口路径为 `/public/testLogin`，在生产环境中不会被外部猜到；如需更严格的安全控制，可后续添加 `@Profile("!prod")` 或配置项开关 |

### 7.2 前端：urls.ts

**改动内容**：

```typescript
testLogin: `${prefix}/capi/user/public/testLogin`, // 测试登录
```

**为什么这样设计**：

| 设计决策 | 原因 |
|---------|------|
| 与现有 URL 风格一致 | 项目中所有 API URL 都集中定义在 `urls.ts` 中，统一维护 |
| 使用 `prefix` 变量 | 开发和生产环境自动切换 baseURL，无需手动修改 |
| 不包含 `{uid}` | Alova 的请求 URL 拼接在 `apis.ts` 中进行，`urls.ts` 只维护基础路径，保持职责单一 |

### 7.3 前端：apis.ts

**改动内容**：

```typescript
/** 测试登录 */
testLogin: (uid: number) => getRequest<string>(`${urls.testLogin}/${uid}`),
```

**为什么这样设计**：

| 设计决策 | 原因 |
|---------|------|
| 使用 `getRequest<string>` | 返回类型为 string（即 token），与 `alovaIns.Get<T>()` 的泛型定义一致 |
| 使用模板字符串拼接 URL | `${urls.testLogin}/${uid}` 动态拼接 uid，复用基础 URL |
| `localCache: 0` | `getRequest` 内部已配置 `localCache: 0`，表示不走前端缓存，每次请求都发向后端 |

### 7.4 前端：LoginBox/index.vue

**改动内容**：新增测试登录区域，包含输入框、按钮和登录逻辑。

**为什么这样设计**：

| 设计决策 | 原因 |
|---------|------|
| 放在登录弹窗底部 | 测试登录是微信登录的替代方案，放在同一弹窗中最符合用户心智模型 |
| 使用 `ElDivider` 分隔 | 视觉上区分正式登录（微信扫码）和测试登录，避免混淆 |
| `ElInput` + `ElButton` 组合 | 使用 Element Plus 组件库，与项目 UI 风格一致；`#append` 插槽将按钮放在输入框右侧，节省空间 |
| `@keyup.enter="onTestLogin"` | 支持回车键触发登录，提升交互体验 |
| `testLoading` 状态 | 防止重复提交，请求期间按钮显示 loading |
| 输入校验 `!uid \|\| uid <= 0` | 防止输入空值或负数，提前拦截无效请求 |
| 保存 `USER_INFO` 到 localStorage | 与微信登录成功后的行为一致，确保页面刷新后登录态不丢失 |
| 调用 `wsIns.initConnect()` | 重新初始化 WebSocket 连接，新连接会带上最新的 token，触发后端认证 |
| 调用 `userStore.getUserDetailAction()` | 获取用户完整信息（头像、昵称等），补全前端状态 |
| `loginStore.loginQrCode = undefined` | 清空二维码，下次打开弹窗时会重新请求（保持原有逻辑不变） |

### 7.5 前端：LoginBox/styles.scss

**改动内容**：

```scss
.test-login-box {
  width: 100%;
  margin-top: 8px;
}
```

**为什么这样设计**：

| 设计决策 | 原因 |
|---------|------|
| 宽度 `100%` | 让输入框占满弹窗宽度，与上方二维码区域对齐 |
| `margin-top: 8px` | 与上方的登录说明文字保持适当间距，视觉上不拥挤 |
| 不加边框/背景色 | 保持简洁，不喧宾夺主；`ElDivider` 已经提供了足够的视觉分隔 |

## 八、最佳实践

### 8.1 测试 UID 的选择

| 场景 | 推荐 UID | 说明 |
|------|---------|------|
| 普通用户测试 | `10001` (ChatGPT) | 数据库预置数据，有头像和昵称 |
| 管理员功能测试 | 需要查询管理员 uid | 调用拉黑等接口需要 `RoleEnum.ADMIN` 权限 |
| 测试自己的业务 | 自定义 uid | 在 `user` 表 INSERT 一条数据，使用自定义 uid |

### 8.2 多个浏览器同时登录

由于 `loginService.login()` 对同一 uid 会复用 Redis 中的 token，多个浏览器用同一 uid 测试登录时：
- Token 相同，后端认为是同一用户
- WebSocket 在线列表中会显示该用户的多条连接
- 这是预期行为，与正式登录一致

### 8.3 切换用户测试

需要测试不同用户时：
1. 清除 localStorage：`localStorage.clear()`
2. 刷新页面
3. 用新的 uid 测试登录

### 8.4 Token 过期处理

测试登录的 Token 有效期为 5 天（与正式登录一致）。如果 Token 过期：
- 后端会返回 `TokenExpired`（WebSocket type=6）
- 前端会自动清除登录态，弹出登录框
- 重新输入 uid 测试登录即可

### 8.5 生产环境注意事项

| 建议 | 说明 |
|------|------|
| 添加环境限制 | 为 `testLogin` 接口添加 `@Profile("!prod")`，确保生产环境不暴露 |
| 添加 IP 白名单 | 通过 Nginx 或 Spring Security 限制测试接口只允许内网访问 |
| 添加操作日志 | 记录测试登录的调用方 IP 和 uid，方便审计 |
| 配置开关 | 通过 `application.yml` 中的配置项控制是否启用测试登录 |

## 九、安全性说明

### 9.1 当前风险

| 风险点 | 等级 | 说明 |
|--------|------|------|
| 任意 uid 登录 | 中 | 知道 uid 即可获取 token，无需密码 |
| 公开接口暴露 | 中 | 接口路径可预测，可能被扫描到 |
| 与生产代码共存 | 低 | 当前没有环境隔离，生产环境也包含此接口 |

### 9.2 缓解措施

**当前已做的防护**：
- 接口路径包含 `testLogin`，具有明确的测试意图，不易被误用
- 需要知道数据库中存在的 uid 才能登录（但 uid 通常可猜测）

**建议后续增强**：

```java
// 方案 1：仅允许特定环境
@Profile("local", "test", "dev")

public ApiResult<String> testLogin(@PathVariable Long uid) {
    AssertUtil.isTrue(testLoginEnabled, "测试登录已禁用");
    ...
}

// 方案 3：添加测试密码
@GetMapping("/public/testLogin/{uid}")
public ApiResult<String> testLogin(
        @PathVariable Long uid,
        @RequestParam String password) {
    AssertUtil.isTrue("your-test-password".equals(password), "密码错误");
    ...
```

## 十、附录：原始登录流程对比

### 10.1 微信登录流程（原始）

```
[前端]                    [后端]                  [微信服务器]
  |                         |                         |
  |-- WS: RequestLoginQrCode ->|                      |
  |                         |-- getQrcodeTicket() --->|
  |                         |<-- qrCode URL ----------|
  |<- WS: LoginQrCode -------|                        |
  |  (展示二维码)              |                       |
  |                         |<-- 用户扫码回调 ---------|
  |<- WS: WaitingAuthorize --|                        |
  |                         |<-- 用户确认登录 ---------|
  |<- WS: LoginSuccess ------|                        |
  |  (含 token)               |                       |
```

### 10.2 测试登录流程（新增）

```
[前端]                    [后端]
  |                         |
  |-- GET /public/testLogin/10001 ->|
  |                         |-- loginService.login(10001)
  |                         |-- JWT 生成 + Redis 存储
  |<-- ApiResult(token) -----|
  |                         |
  |-- WS: 连接 ws://...?token=xxx ->|
  |                         |-- loginService.verify(token)
  |<-- WS: LoginSuccess -----|
```

### 10.3 关键差异

| 对比项 | 微信登录 | 测试登录 |
|--------|---------|---------|
| 触发方式 | 打开登录弹窗自动请求二维码 | 用户手动输入 uid 点击登录 |
| 依赖外部服务 | 微信 API | 无 |
| Token 来源 | `loginService.login(uid)` | `loginService.login(uid)` |
| WebSocket 认证 | 正常 | 正常 |
| 前端状态 | `LoginStatus.Success` | `LoginStatus.Success` |
| 数据一致性 | 真实数据 | 真实数据 |
