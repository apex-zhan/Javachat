## **1. 本地缓存怎么实现的？**

答：使用 caffeine

```java
@Service
public class LocalCacheService {
    private Cache<String, String> tokenCache;      // Token缓存
    private Cache<String, String> userInfoCache;   // 用户信息缓存
    private Cache<String, Object> generalCache;    // 通用缓存

    @PostConstruct
    public void init() {
        // 初始化Token缓存 - 10分钟过期，最大10000个
        tokenCache = Caffeine.newBuilder()
                .maximumSize(10000)
                .expireAfterWrite(10, TimeUnit.MINUTES)
                .expireAfterAccess(5, TimeUnit.MINUTES)
                .recordStats()
                .build();

        // 初始化用户信息缓存 - 30分钟过期，最大5000个
        userInfoCache = Caffeine.newBuilder()
                .maximumSize(5000)
                .expireAfterWrite(30, TimeUnit.MINUTES)
                .expireAfterAccess(10, TimeUnit.MINUTES)
                .recordStats()
                .build();

        // 初始化通用缓存 - 15分钟过期，最大2000个
        generalCache = Caffeine.newBuilder()
                .maximumSize(2000)
                .expireAfterWrite(15, TimeUnit.MINUTES)
                .expireAfterAccess(5, TimeUnit.MINUTES)
                .recordStats()
                .build();
    }

    public String get(String key) {
        if (key == null) {
            return null;
        }

        // 根据key类型选择不同的缓存
        if (key.contains("userToken")) {
            return tokenCache.getIfPresent(key);
        } else if (key.contains("userInfo") || key.contains("userSummary")) {
            return userInfoCache.getIfPresent(key);
        } else {
            Object value = generalCache.getIfPresent(key);
            return value != null ? value.toString() : null;
        }
    }

    // ... put、delete等其他方法
}

```

## **4. 如何保证 redis 和数据库的一致性？**

答：

4.1 当前提交的代码实现方案是旁路缓存（ Cahe-Aside Pattern）

读取流程：

// 1️⃣ 先查 Redis 缓存
// 2️⃣ 计算缓存未命中的 ID
// 3️⃣ 从数据库加载未命中的数据
// 4️⃣ 回写 Redis（设置过期时间 5 分钟）
// 5️⃣ 合并结果返回

更新流程：

// 1️⃣ 先更新数据库
// 2️⃣ 再删除缓存（延迟双删的第一次删除）（@Transactional 确保数据库更新成功后才删除缓存）
// 3️⃣ 发布用户信息更新事件（spring 事件机制）

4.2 本地消息表保障最终一致性

// 1️⃣ 保存消息到数据库（本地事务）
// 2️⃣ 发送 MQ（带@SecureInvoke 保证）

执行流程：

```java
1. 开启数据库事务
   ↓
2. 保存message到数据库
   ↓
3. 调用sendSecureMsg()
   ↓ @SecureInvoke AOP拦截
   ↓
4. 序列化方法调用信息
   {
     "className": "MQProducer",
     "methodName": "sendSecureMsg",
     "args": [...]
   }
   ↓
5. 保存到secure_invoke_record表（同一事务）
   ↓
6. 提交事务
   - message表已提交 ✅
   - secure_invoke_record表已提交 ✅
   ↓
7. 事务提交后（TransactionSynchronization.afterCommit）
   ↓
8. 异步执行MQ发送
   - 成功：删除secure_invoke_record记录 ✅
   - 失败：等待定时任务重试 ⏰
   ↓
9. 定时任务（每5秒扫描）
   - 查询待重试记录
   - 反射调用方法
   - 指数退避重试（2分钟→4分钟→8分钟...）
```

4.3 Spring 事务事件监听

使用`@TransactionalEventListener`来保证事件在事务提交后才触发。

一致性保障机制：

✅ BEFORE_COMMIT：事务提交前触发，保证数据已持久化
✅ AFTER_COMMIT（默认）：事务提交后触发，避免事务回滚导致的不一致
✅ fallbackExecution = true：即使没有事务也会执行，提高容错性

4.4 批量缓存框架的一致性保障（AbstractRedisStringCache）

`@Override`
`public Map<IN, OUT> getBatch(List<IN> req) {`
`// 1. 批量查询Redis`
`// 2. 计算缓存未命中的ID`
`// 3. 批量查询数据库`
`// 4. 批量回写Redis（设置过期时间）`
`// 5. 合并结果`
`}`
一致性保障机制：

✅ 过期时间：所有缓存都设置过期时间（5 分钟），避免长期不一致
✅ 主动失效：数据更新时调用 delete()主动删除缓存
✅ 批量操作原子性：使用 Redis Pipeline 保证批量操作的原子性

4.5 目前正在改进的方案是：JetCache 集成进一步增强缓存一致性

`JetCache 核心层`
`│  - CacheManager（缓存管理）`
`│  - CacheMonitor（缓存监控）`

执行流程：

1. `查询本地缓存（Caffeine）`
   `├─ 命中 → 直接返回（< 1ms）✅`
   `└─ 未命中 ↓`
2. `查询远程缓存（Redis）`
   `├─ 命中 → 更新本地缓存 → 返回（< 10ms）✅`
   `└─ 未命中 ↓`
3. `查询数据库`
   `└─ 更新两级缓存 → 返回（< 100ms）✅`

5.两种方案的对比分析

已提交代码方案（当前实现）
优点：
✅ 简单可靠：旁路缓存模式，逻辑清晰
✅ 本地消息表：保证分布式事务最终一致性
✅ 批量优化：自研批量缓存框架，性能提升 20 倍
✅ 事务事件：@TransactionalEventListener 保证事件在事务提交后触发
缺点：
❌ 单级缓存：只有 Redis，没有本地缓存
❌ 手动管理：需要手动调用 delete()删除缓存
❌ 缺乏监控：没有缓存命中率、加载时间等监控指标
❌ 一致性窗口：更新数据库到删除缓存之间有短暂不一致

一致性保障策略：
| 场景 | 策略 | 一致性级别 | |-----|------|-----------| | 读取数据 | 先查缓存，未命中查数据库并回写 | 最终一致 | | 更新数据 | 先更新数据库，再删除缓存 | 最终一致 | | 分布式事务 | 本地消息表 + 定时重试 | 最终一致 | | 事件通知 | @TransactionalEventListener | 最终一致 |\*\*

| 场景 | 策略 | 一致性级别 | |-----|------|-----------| | 读取数据 | 本地缓存 → Redis → 数据库 | 最终一致 | | 更新数据 | 更新数据库 + @CacheInvalidate 自动失效 | 最终一致 | | 缓存同步 | Redis 命中时自动更新本地缓存 | 最终一致 | | 缓存穿透 | 缓存 null 值 + 布隆过滤器 | 强一致 | | 缓存击穿 | 分布式锁 + 单线程加载 | 强一致 | | 缓存雪崩 | 过期时间随机化 | 最终一致 |

## **5.本地消息表分布式一致性，什么场景？为什么选择这个方案？一定要成功怎么做？**

**问题分析：**

- 事务只能保证 DB 操作的原子性

- MQ 发送失败，DB 已提交 → **数据不一致**

- 网络波动、MQ 宕机 → **消息丢失**

| 方案              | 核心原理                           | 一致性类型 | 性能表现 | 核心优点     | 主要缺点           | 实现复杂度 | 业务侵入性         | 适用场景                         |
| ----------------- | ---------------------------------- | ---------- | -------- | ------------ | ------------------ | ---------- | ------------------ | -------------------------------- |
| 2PC（两阶段提交） | 协调者 + 参与者，分准备 + 提交阶段 | 强一致     | 低       | 强一致性     | 同步阻塞、性能差   | 中         | 无（数据库层实现） | 金融、支付等强一致需求场景       |
| 3PC（三阶段提交） | 基于 2PC 增加超时机制              | 强一致     | 中低     | 减少阻塞概率 | 实现复杂           | 高         | 无                 | 对一致性要求高的核心业务         |
| TCC               | Try-Confirm-Cancel 三段逻辑        | 最终一致   | 高       | 灵活、性能好 | 业务侵入大         | 高         | 强                 | 订单、库存等业务定制化场景       |
| 本地消息表        | 消息持久化 + 重试机制              | 最终一致   | 高       | 简单、性能好 | 仅支持最终一致     | 低         | 中                 | 大部分通用业务、非强实时场景     |

|                   |                                    |            |          |              |                    |            |                    |                                  |

**为什么选择本地消息表？**

✅ **实现简单**：只需一张表 + 定时任务

✅ **通用性强**：适用于所有第三方调用

✅ **性能好**：异步执行，不阻塞主流程

✅ **可靠性高**：持久化 + 重试保证最终成功

## 6.深分页问题，项目游标翻页详细分析  ？

### 📚 MallChat项目游标翻页详细分析  
  
#### 一、什么是游标翻页？  
  
游标翻页（Cursor Pagination）是一种比传统分页（Page Pagination）更高效的分页方式，特别适用于数据频繁更新的场景。  
  
**传统分页 vs 游标翻页：**  
- **传统分页**：使用`LIMIT offset, size`，存在数据重复或遗漏问题，深度分页性能差  
- **游标翻页**：基于唯一标识（游标）定位，避免数据重复，性能更稳定  
  
---

#### 三、两种实现方式  
  
项目提供了两种游标翻页实现：**MySQL方式**和**Redis ZSet方式**  
  
##### 1. **基于MySQL的游标翻页**  
  
```java:57:79:mallchat-chat-server/src/main/java/com/abin/mallchat/common/common/utils/CursorUtils.java  
public static <T> CursorPageBaseResp<T> getCursorPageByMysql(IService<T> mapper, CursorPageBaseReq request, Consumer<LambdaQueryWrapper<T>> initWrapper, SFunction<T, ?> cursorColumn) {  
    //游标字段类型  
    Class<?> cursorType = LambdaUtils.getReturnType(cursorColumn);    LambdaQueryWrapper<T> wrapper = new LambdaQueryWrapper<>();    //额外条件  
    initWrapper.accept(wrapper);    //游标条件  
    if (StrUtil.isNotBlank(request.getCursor())) {        wrapper.lt(cursorColumn, parseCursor(request.getCursor(), cursorType));    }    //游标方向  
    wrapper.orderByDesc(cursorColumn);  
    Page<T> page = mapper.page(request.plusPage(), wrapper);    //取出游标  
    String cursor = Optional.ofNullable(CollectionUtil.getLast(page.getRecords()))            .map(cursorColumn)            .map(CursorUtils::toCursor)            .orElse(null);    //判断是否最后一页  
    Boolean isLast = page.getRecords().size() != request.getPageSize();    return new CursorPageBaseResp<>(cursor, isLast, page.getRecords());}  
```  
  
**实现原理：**  
1. **第一次请求**：cursor为空，直接按游标字段倒序查询前N条  
2. **后续请求**：添加条件 `WHERE 游标字段 < 上次游标值`，继续查询  
3. **提取新游标**：取当前页最后一条记录的游标字段值  
4. **判断结束**：如果返回数据量 < pageSize，说明是最后一页  
  
**实际使用示例：**  
  
```java:33:39:mallchat-chat-server/src/main/java/com/abin/mallchat/common/chat/dao/MessageDao.java  
public CursorPageBaseResp<Message> getCursorPage(Long roomId, CursorPageBaseReq request, Long lastMsgId) {  
    return CursorUtils.getCursorPageByMysql(this, request, wrapper -> {        wrapper.eq(Message::getRoomId, roomId);        wrapper.eq(Message::getStatus, MessageStatusEnum.NORMAL.getStatus());        wrapper.le(Objects.nonNull(lastMsgId), Message::getId, lastMsgId);    }, Message::getId);}  
```  
  
**SQL示意：**  
```sql

ORDER BY id DESC LIMIT 10;  
  
-- 第二次请求（cursor=100）
```  

##### 2. **基于Redis ZSet的游标翻页**  
  
```java:37:55:mallchat-chat-server/src/main/java/com/abin/mallchat/common/common/utils/CursorUtils.java  
public static <T> CursorPageBaseResp<Pair<T, Double>> getCursorPageByRedis(CursorPageBaseReq cursorPageBaseReq, String redisKey, Function<String, T> typeConvert) {  
    Set<ZSetOperations.TypedTuple<String>> typedTuples;    if (StrUtil.isBlank(cursorPageBaseReq.getCursor())) {//第一次  
        typedTuples = RedisUtils.zReverseRangeWithScores(redisKey, cursorPageBaseReq.getPageSize());    } else {        typedTuples = RedisUtils.zReverseRangeByScoreWithScores(redisKey, Double.parseDouble(cursorPageBaseReq.getCursor()), cursorPageBaseReq.getPageSize());    }    List<Pair<T, Double>> result = typedTuples            .stream()            .map(t -> Pair.of(typeConvert.apply(t.getValue()), t.getScore()))            .sorted((o1, o2) -> o2.getValue().compareTo(o1.getValue()))            .collect(Collectors.toList());    String cursor = Optional.ofNullable(CollectionUtil.getLast(result))            .map(Pair::getValue)            .map(String::valueOf)            .orElse(null);    Boolean isLast = result.size() != cursorPageBaseReq.getPageSize();    return new CursorPageBaseResp<>(cursor, isLast, result);}  
```  
  
**实现原理：**  
1. **第一次请求**：使用`ZREVRANGE`获取前N个成员  
2. **后续请求**：使用`ZREVRANGEBYSCORE`获取score < cursor的前N个成员  
3. **利用ZSet的score**：作为游标值，自动排序  
4. **返回结果**：包含成员值和score的Pair对  
  
**实际使用示例：**


支持Date、Long、String等多种类型作为游标

如果返回数据量少于请求量，说明已到最后一页

28.分布式锁怎么做的?（连环问）

正确的顺序应该是：

1. 先获取分布式锁
2. 再开启事务
3. 执行业务逻辑
4. 提交事务
5. 释放分布式锁
   这样才能确保在分布式环境下的数据一致性。

通过`@Order(0)`注解，将分布式锁切面的优先级设置为最高（数值越小优先级越高），确保它在事务切面之前执行。

有了`@Order(0)`注解后，执行顺序变为：

1. RedissonLockAspect 的 around 方法先执行
2. 获取分布式锁
3. 调用 joinPoint.proceed()继续执行
4. Transactional 的切面执行，开启事务
5. 执行业务方法
6. 提交事务
7. 返回 RedissonLockAspect，释放分布式锁

## 33 项目的AI支持多轮对话吗？

项目当前不支持AI多轮对话功能。

每次AI请求均为独立的单轮交互，尽管项目会将问答记录保存至ai_conversation表，但该表仅实现“只写不读”的功能——后续AI请求不会自动查询该表中的历史上下文并注入当前交互中。

无法支持多轮对话的主要原因如下：

1. 请求参数缺失会话标识：QuestionRequest、RAGQueryRequest等DTO（数据传输对象）中未包含conversationId或sessionId字段，无法有效区分不同的对话线程，导致系统无法关联同一用户的连续请求。
    
2. 缺乏读取历史记录的代码：AIAssistantServiceImpl、RAGServiceImpl等核心服务类在构造Prompt（提示词）时，未编写查询该用户历史消息的相关代码，无法获取过往对话内容。
    
3. 未引入LangChain4j的ChatMemory组件：未集成MessageWindowChatMemory、TokenWindowChatMemory等ChatMemory相关组件，无法实现对话上下文的存储与管理。
    
4. Prompt构建为纯单轮模式：当前Prompt仅由系统提示 + 当前问题（若有RAG检索场景，则增加RAG检索片段）构成，未包含任何历史消息对，无法形成上下文关联。
    

项目文档已明确将“支持多轮对话上下文”列为下一步待实现的功能。若前端现阶段需要实现上下文关联，可通过手动将历史消息拼接至QuestionRequest.context字段的方式，将历史对话内容传入后端。

      public User getHotUser(Long uid) {
          String key = "user:info:" + uid;
          String lockKey = "lock:user:" + uid;

          User user = RedisUtils.get(key, User.class);
          if (user == null) {
              try {
                  // 获取分布式锁，防止多个线程同时重建缓存
                  if (RedisUtils.tryLock(lockKey, 10, TimeUnit.SECONDS)) {
                      // 双重检查：获取锁后再次检查缓存
                      user = RedisUtils.get(key, User.class);
                      if (user == null) {
                          // 从数据库加载并重建缓存
                          user = userDao.getById(uid);
                          if (user != null) {
                              RedisUtils.set(key, user, 300);
                          }
                      }
                  } else {
                      // 获取锁失败，暂时返回过期数据或默认值
                      Thread.sleep(50);
                      return getHotUser(uid); // 递归重试
                  }
              } finally {
                  RedisUtils.unlock(lockKey);
              }
          }
          return user;
      }

      Map<Long, User> resultMap = cachedUsers.stream()

          .filter(uid -> !resultMap.containsKey(uid))
          .collect(Collectors.toList());

      if (CollUtil.isNotEmpty(needLoadUids)) {

              .collect(Collectors.toMap(
                  user -> RedisKey.getKey(RedisKey.USER_INFO_STRING, user.getId()),
                  Function.identity()
              ));
          RedisUtils.mset(redisMap, 5 * 60);  // 批量回写，原子性

          resultMap.putAll(dbUsers.stream()
              .collect(Collectors.toMap(User::getId, Function.identity())));
      }

      return resultMap;

  }

// 以 UserInfoCache 为例
@Component
public class UserInfoCache extends AbstractRedisStringCache<Long, User> {

    public Map<Long, User> getBatch(List<Long> uidList) {
        // 1️⃣ 先查Redis缓存
        List<String> keys = uidList.stream()
            .map(uid -> "user:info:" + uid)
            .collect(Collectors.toList());
        List<User> cachedUsers = RedisUtils.mget(keys, User.class);

        // 2️⃣ 计算缓存未命中的ID
        List<Long> missIds = new ArrayList<>();
        for (int i = 0; i < cachedUsers.size(); i++) {
            if (cachedUsers.get(i) == null) {
                missIds.add(uidList.get(i));
            }
        }

        // 3️⃣ 从数据库加载未命中的数据
        Map<Long, User> dbUsers = new HashMap<>();
        if (!missIds.isEmpty()) {
            List<User> users = userDao.listByIds(missIds);
            dbUsers = users.stream()
                .collect(Collectors.toMap(User::getId, Function.identity()));

            // 4️⃣ 回写Redis（设置过期时间5分钟）
            Map<String, User> redisMap = dbUsers.entrySet().stream()
                .map(e -> Pair.of("user:info:" + e.getKey(), e.getValue()))
                .collect(Collectors.toMap(Pair::getFirst, Pair::getSecond));
            RedisUtils.mset(redisMap, 5 * 60L);
        }

        // 5️⃣ 合并结果返回
        return mergeResults(cachedUsers, dbUsers);
    }

}

✅ 读取时自动同步：缓存未命中时从数据库加载并更新缓存

## 二、多端同步的核心设计：一用户多 Channel

核心数据结构（WebSocketServiceImpl.java:75）：


当用户同时登录 手机 + PC + Web 时，ONLINE_UID_MAP 中该 uid 对应的 CopyOnWriteArrayList 会持有 3 个 Channel。

```
@Override
public void sendToUid(WSBaseResp<?> wsBaseResp, Long uid) {
    CopyOnWriteArrayList<Channel> channels = ONLINE_UID_MAP.get(uid);
    if (CollectionUtil.isEmpty(channels)) return;
    // 遍历所有 Channel，异步推送
    channels.forEach(channel -> {
        threadPoolTaskExecutor.execute(() -> sendMsg(channel, wsBaseResp));
    });
}
```

```
    public void onMessage(PushMessageDTO message) {
        switch (WSPushTypeEnum.of(message.getPushType())) {
            case USER:
                message.getUidList().forEach(uid -> webSocketService.sendToUid(message.getWsBaseMsg(), uid));
                break;
            case ALL:

                break;
```

设计原理：

- 每个服务器实例维护自己的本地 ONLINE_UID_MAP
- MQ 广播后，每个实例都收到消息，各自检查本地有哪些 Channel 属于目标用户
- 无需中心化的连接注册中心，无需 Session Sticky，天然支持水平扩展

```
private boolean offline(Channel channel, Optional<Long> uidOptional) {
    ONLINE_WS_MAP.remove(channel);
```

## 十、总结

MallChat 的多端同步方案是一个 轻量级、可水平扩展 的设计：

1. 单实例内：通过 ConcurrentHashMap + CopyOnWriteArrayList 实现一用户多 Channel 的本地推送
2. 跨实例间：通过 RocketMQ 广播消费 让每个实例只推自己管理的本地连接
3. 状态一致性：基于 read_time 的查询模型保证多端未读数一致
4. 在线状态：仅在用户所有设备断连后才标记离线，避免状态抖动

这套方案无需 Redis Pub/Sub、无需专门的连接代理（如 Nginx 的 ip_hash），在中小规模集群下非常高效。
4. 理论上的完整多端同步方案（项目笔记中提到的）
项目文档中详细描述了一个更完善的多端同步方案，虽然暂未实现，但可以作为面试回答：

核心思路：客户端维护游标
传统方案的问题：
- 服务端维护每个端的 ACK 状态 → 复杂且难扩展
- 每个端都需要独立的收信箱 → 资源浪费

改进方案：
- 客户端维护自己的阅读游标（最后读到的消息 ID）
- 服务端只需要维护全局递增的消息 ID
- 拉取消息时带上游标，服务端返回 ID > 游标的所有消息

工作流程：
消息 ID 设计：全局递增（MallChat 使用雪花算法生成）
客户端存储：每个端本地存储自己的阅读游标

拉取消息：
手机端游标=2，请求时查询 ID>2 的消息 → 返回 3,4
电脑端游标=1，请求时查询 ID>1 的消息 → 返回 2,3,4
新消息推送：服务端推送给该用户的所有在线设备

5. 面试回答建议
你可以这样回答：

"MallChat 目前主要是 Web 端项目，支持同一用户在多个浏览器标签页登录。项目通过 ConcurrentHashMap<Long,CopyOnWriteArrayList<Channel>> 维护一个用户的多个 WebSocket 连接，当有新消息时会推送给该用户的所有在线设备。

对于聊天记录同步，目前采用的是简单方案：每次登录拉取最新消息，历史消息通过翻页加载。

如果要实现完整的多端同步（比如手机 App + PC 端），我们可以采用客户端游标方案：

每个客户端维护自己读到的最后一条消息 ID（游标）
消息 ID 全局递增（我们用雪花算法保证）
拉取消息时带上游标，服务端返回所有大于该游标的消息
这样避免了服务端维护多端状态的复杂性，扩展性更好"

### 十、总结  
  
MallChat的联系人列表实现体现了以下**核心亮点**：  
  
✅ **双列表合并**：基础会话 + 热门房间，支持登录/未登录场景  ✅ **游标翻页**：基于`activeTime`，性能稳定，数据一致  ✅ **批量优化**：避免N+1查询，一次性加载所有关联数据  ✅ **未读数计算**：基于`read_time`字段，精确统计  ✅ **多级缓存**：Redis + 本地缓存，减少数据库压力  ✅ **ON DUPLICATE KEY**：一条SQL解决插入/更新问题  ✅ **策略模式**：优雅处理不同消息类型展示

```plaintext  
public CursorPageBaseResp<ChatRoomResp> getContactPage(CursorPageBaseReq request, Long uid) {  
    // 查出用户要展示的会话列表  
    CursorPageBaseResp<Long> page;    if (Objects.nonNull(uid)) {        Double hotEnd = getCursorOrNull(request.getCursor());        Double hotStart = null;        // 用户基础会话  
        CursorPageBaseResp<Contact> contactPage = contactDao.getContactPage(uid, request);        List<Long> baseRoomIds = contactPage.getList().stream().map(Contact::getRoomId).collect(Collectors.toList());        if (!contactPage.getIsLast()) {            hotStart = getCursorOrNull(contactPage.getCursor());        }        // 热门房间  
        Set<ZSetOperations.TypedTuple<String>> typedTuples = hotRoomCache.getRoomRange(hotStart, hotEnd);        List<Long> hotRoomIds = typedTuples.stream().map(ZSetOperations.TypedTuple::getValue).filter(Objects::nonNull).map(Long::parseLong).collect(Collectors.toList());        baseRoomIds.addAll(hotRoomIds);        // 基础会话和热门房间合并  
        page = CursorPageBaseResp.init(contactPage, baseRoomIds);    } else {// 用户未登录，只查全局房间  
        CursorPageBaseResp<Pair<Long, Double>> roomCursorPage = hotRoomCache.getRoomCursorPage(request);        List<Long> roomIds = roomCursorPage.getList().stream().map(Pair::getKey).collect(Collectors.toList());        page = CursorPageBaseResp.init(roomCursorPage, roomIds);    }    if (CollectionUtil.isEmpty(page.getList())) {        return CursorPageBaseResp.empty();    }    // 最后组装会话信息（名称，头像，未读数等）  
    List<ChatRoomResp> result = buildContactResp(uid, page.getList());    return CursorPageBaseResp.init(page, result);}
```  

## RAG的基本流程

准备（提问前）：分片  ---> 索引

回答（提问后）：召回  --->  重排  --->  生成


分片：
按数字分、字母分、段落分、文本分等等


索引：
1. 通过 **Embedding** 将片段文本转换为**向量**
2. 将片段文本和片段向量存入**向量数据库**中



``` java

原始文档 → 预处理 → 分块 → 向量化 → 向量数据库（离线）
                                         ↑ 
用户查询 → 查询向量化 → 语义检索 ←------（在线） 
										 ↓
						 检索结果 + 查询 → 提示构建 → LLM生成 → 最终回答
```

### 关键技术要点

|步骤|核心技术|常用工具|核心目标|
|---|---|---|---|
|分块|语义分割|LangChain TextSplitter|平衡检索精度与上下文完整性|
|向量化|嵌入模型|Sentence-BERT、OpenAI Embeddings|语义的数学表示|
|存储|向量数据库|Milvus、ChromaDB|高效相似度检索|
|检索|相似性搜索|FAISS、ANN 算法|精准匹配相关知识|
|生成|提示工程|LangChain PromptTemplate|引导模型生成高质量回答|







# 35. 项目的多轮对话意图识别这么做的？

我来搜索项目中关于多轮对话意图识别的实现。

根据代码分析，项目的**多轮对话实现方式**如下：

## 核心实现机制

### 1. **会话管理（Session Management）**

```
// AIAssistantServiceImpl.java 第60-72行
if (request.getConversationId() == null || request.getConversationId().trim().isEmpty()) {
    sessionId = generateSessionId();  // 生成新会话ID
    isNewSession = true;
} else {
    sessionId = request.getConversationId();  // 使用已有会话ID
    isNewSession = false;
}
```

- 使用 `sessionId` 标识多轮对话
- 首次对话生成UUID，后续对话携带相同ID保持上下文

### 2. **对话历史存储**

```
// AIConversation.java 实体
- sessionId: 会话ID
- userId: 用户ID
- userInput: 用户输入
- aiResponse: AI回复
- conversationType: 对话类型（QA/RAG/SUMMARY）
- createTime: 创建时间
```

- 每次对话后自动保存到 `ai_conversation` 表
- 支持按 `sessionId` 查询历史记录

### 3. **上下文构建**

```
// buildConversationMessages() 方法（第147-180行）
1. 添加系统提示
2. 添加可选的背景信息
3. 加载历史对话（最近20轮）
4. 添加当前问题
5. 检查token数量，超出则截断
```

- 使用 LangChain4j 的 `ChatMessage` 类型
- 消息顺序：SystemMessage → 历史UserMessage → 历史AiMessage → 当前UserMessage

### 4. **Token管理**

```
// truncateMessagesIfNeeded() 方法（第203-238行）
- 使用 OpenAiTokenizer 精确计算token数量
- 保留系统提示和最近消息
- 从后往前添加，直到接近限制（80%余量）
- 保留20%余量给生成响应
```

### 5. **意图识别方式**

**当前实现：基于LLM的隐式意图识别**

- **没有专门的意图识别模型**
- 依赖 LLM（GPT-3.5）理解对话上下文
- 通过历史对话和系统提示让LLM推断用户意图
- 属于**端到端**的方式，LLM直接理解并响应

**代码体现：**

```
// 构造的Prompt包含完整上下文
messages.add(new SystemMessage(qaSystemPrompt));  // 系统提示
// 历史对话...
messages.add(new UserMessage(request.getQuestion()));  // 当前问题

// LLM根据完整上下文理解意图并生成回答
llmService.streamChat(messages, options)
```

### 6. **RAG场景的多轮对话**

```
// RAGServiceImpl.java 也保存对话历史
conversation.setConversationType(ConversationType.RAG.name());
conversation.setRetrievedChunkIds(objectMapper.writeValueAsString(chunkIds));
```

- RAG查询也保存对话历史
- 记录检索到的文档分块ID
- 但**没有实现RAG场景的多轮对话上下文**（每次查询独立）

## 总结

**项目的多轮对话意图识别特点：**

1. **简单实用**：依赖LLM的强大理解能力，无需额外模型
2. **会话管理**：通过sessionId维护对话上下文
3. **历史加载**：加载最近20轮对话
4. **Token控制**：智能截断避免超限
5. **无显式意图分类**：不进行意图分类（如查询、闲聊、命令等）
6. **RAG场景待完善**：RAG查询目前是单轮的，未结合对话历史

**如果需要更复杂的意图识别**，可以考虑：

- 添加专门的意图分类模型
- 实现对话状态跟踪（Dialogue State Tracking）
- 在RAG场景中结合对话历史进行检索
