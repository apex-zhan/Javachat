# 生产环境优化指南

## 概述

本文档详细说明了 AI Assistant & RAG 系统的生产环境优化方案，包括缓存优化、批量处理、多 LLM 提供商支持、Qdrant 性能调优和 Mock 模式开发优化。

## 1. 缓存优化

### 1.1 文档元数据缓存

**实现类**: `DocumentMetadataCache`

**功能**:
- 缓存文档基本信息（标题、类型、大小、状态等）
- 支持单个和批量查询
- 自动失效和手动失效
- 两级缓存（本地 + Redis）

**缓存策略**:
- 缓存时间：30分钟
- 缓存类型：BOTH（本地 + Redis）
- 空值缓存：是（防止缓存穿透）

**使用示例**:
```java
@Autowired
private DocumentMetadataCache documentMetadataCache;

// 单个查询
KnowledgeDocument doc = documentMetadataCache.getDocumentMetadata(documentId);

// 批量查询
List<Long> ids = Arrays.asList(1L, 2L, 3L);
Map<Long, KnowledgeDocument> docs = documentMetadataCache.getDocumentMetadataBatch(ids);

// 失效缓存
documentMetadataCache.invalidateDocumentMetadata(documentId);
```

### 1.2 索引状态缓存

**实现类**: `IndexStatusCache`

**功能**:
- 缓存文档索引状态（PENDING, INDEXING, COMPLETED, FAILED）
- 支持快速查询和批量查询
- 自动过期和手动失效

**缓存策略**:
- 缓存时间：10分钟（索引状态变化较频繁）
- 缓存类型：Redis（需要跨实例共享）
- 空值缓存：否

**使用示例**:
```java
@Autowired
private IndexStatusCache indexStatusCache;

// 查询索引状态
String status = indexStatusCache.getIndexStatus(documentId);

// 检查索引是否就绪
boolean ready = indexStatusCache.isIndexReady(documentId);

// 更新索引状态
indexStatusCache.updateIndexStatus(documentId, "COMPLETED");
```

### 1.3 查询结果缓存

**实现类**: `QueryResultCache`

**功能**:
- 缓存热门查询的向量检索结果
- 减少向量数据库查询压力
- 提升响应速度

**缓存策略**:
- 缓存时间：5分钟（查询结果时效性要求较高）
- 缓存类型：Redis
- 缓存键：基于问题文本的MD5哈希 + documentId + topK

**使用示例**:
```java
@Autowired
private QueryResultCache queryResultCache;

// 尝试从缓存获取
List<SearchResult> results = queryResultCache.getQueryResult(question, documentId, topK);

if (results == null) {
    // 缓存未命中，执行检索
    results = vectorService.search(queryVector, topK, documentId);
    
    // 缓存结果
    queryResultCache.cacheQueryResult(question, documentId, topK, results);
}
```

## 2. 批量处理优化

### 2.1 批量向量生成

**实现类**: `BatchProcessingService`

**优化点**:
- 使用 LangChain4j 的 `embedAll` 方法批量生成向量
- 一次 API 调用生成多个向量，减少网络往返
- 支持大批量数据自动分批处理
- 支持并发处理进一步提升性能

**性能对比**:
- 循环调用：100个文本需要100次API调用
- 批量调用：100个文本只需要1-2次API调用（根据批次大小）
- 性能提升：约50-100倍

**配置参数**:
```yaml
ai:
  batch:
    embedding:
      size: 100  # 每批次向量生成数量
    database:
      size: 500  # 每批次数据库操作数量
    concurrent:
      threads: 4  # 并发处理线程数
```

**使用示例**:
```java
@Autowired
private BatchProcessingService batchProcessingService;

// 批量生成向量（自动分批）
List<String> texts = Arrays.asList("text1", "text2", ...);
List<float[]> embeddings = batchProcessingService.batchGenerateEmbeddings(texts);

// 并发批量生成（高性能版本）
List<float[]> embeddings = batchProcessingService.concurrentBatchGenerateEmbeddings(texts);
```

### 2.2 批量数据库操作

**优化点**:
- 使用 MyBatis-Plus 的 `saveBatch` 方法批量插入
- 减少数据库连接次数
- 提升写入性能

**性能对比**:
- 单条插入：1000条数据需要1000次数据库操作
- 批量插入：1000条数据只需要2-5次数据库操作
- 性能提升：约200-500倍

### 2.3 批量向量存储

**优化点**:
- Qdrant 原生支持批量 upsert
- 一次性插入多个向量，减少网络开销
- 自动处理大批量数据分批

**实现位置**: `QdrantVectorService.storeVectors()`

## 3. 多 LLM 提供商支持

### 3.1 支持的提供商

**已实现**:

1. **Qwen (Ollama)** [推荐]
   - 模型：Qwen2.5-14B
   - 部署方式：Ollama 本地
   - 中文能力强，显存需求适中

2. **Llama (Ollama)** [备选]
   - 模型：Llama3-70B
   - 部署方式：Ollama 本地
   - 英文/代码能力强

3. **OpenAI** [兼容]
   - 模型：GPT-3.5 / GPT-4
   - 部署方式：OpenAI API
   - 无需本地 GPU

4. **ChatGLM** [兼容]
   - 模型：ChatGLM 系列
   - 部署方式：智谱 API
   - 中文优化

5. **Mock** [开发测试]
   - 返回固定模拟回复
   - 无需外部依赖

### 3.2 提供商切换

**实现类**: `LLMServiceFactory`

**功能**:
- 管理多个 LLM 提供商
- 根据配置动态切换
- 支持降级和故障转移
- 支持运行时切换

**配置示例**:
```yaml
langchain4j:
  llm:
    provider: qwen          # 默认提供商
    fallback-provider: llama  # 降级提供商

ollama:
  base-url: http://localhost:11434
  model-name: qwen2.5:14b
  temperature: 0.7
  timeout: 120s
```

**使用示例**:
```java
@Autowired
private LLMServiceFactory llmServiceFactory;

// 获取默认服务
LLMService service = llmServiceFactory.getDefaultService();

// 获取指定提供商服务
LLMService qwenService = llmServiceFactory.getService(LLMProvider.QWEN_OLLAMA);
LLMService llamaService = llmServiceFactory.getService(LLMProvider.LLAMA);

// 获取降级服务
LLMService fallbackService = llmServiceFactory.getFallbackService();

// 运行时切换提供商
llmServiceFactory.switchDefaultProvider(LLMProvider.LLAMA);
```

## 4. Qdrant 性能调优

### 4.1 连接管理

**实现类**: `QdrantVectorService`

**功能**:
- 使用 Qdrant gRPC 客户端
- 连接复用，减少连接开销
- 支持 TLS 和 API Key 认证

**配置参数**:
```yaml
qdrant:
  host: localhost
  port: 6334              # gRPC 端口
  api-key:                # 认证密钥（可选）
  collection-name: mallchat_knowledge
  grpc-timeout: 30
  use-tls: false
```

**注意**: Java SDK 使用 gRPC 端口 6334，不是 REST 端口 6333。

### 4.2 动态向量配置

**核心优势**:
- 同一 Collection 支持 1024 维（bge）和 768 维（m3e）
- 切换 Embedding 模型无需重建 Collection
- 维度由第一个插入的向量自动确定

**实际代码**:
```java
Collections.CollectionOperationResponse response = qdrantClient.createCollectionAsync(
        collectionName,
        Collections.VectorParams.newBuilder()
                .setDistance(Collections.Distance.Cosine)
                .setOnDisk(true)      // 向量落盘，降低内存
                .setDynamic(true)     // 开启动态向量
                .build()
).get();
```

### 4.3 索引与搜索优化

**距离度量**: Cosine（推荐用于语义检索）

**参数调优**:

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `on_disk` | `true` | 向量落盘，降低内存 |
| `dynamic` | `true` | 支持动态维度 |
| `topK` | 5 | 返回最相似的 K 个结果 |
| `similarity-threshold` | 0.7 | 过滤低质量结果 |

### 4.4 分片与副本策略

**分片配置**:
- 小规模（< 100万向量）：默认分片
- 中等规模（100万-1000万）：2-4个分片
- 大规模（> 1000万）：4-8个分片

**副本配置**:
- 开发环境：1个副本
- 生产环境：2-3个副本（高可用）

**生产环境推荐配置**:
```yaml
qdrant:
  host: qdrant-cluster
  port: 6334
  collection-name: mallchat_knowledge_prod
  grpc-timeout: 30
  replication-factor: 2
  write-consistency-factor: 1
```

### 4.5 性能调优建议

**1. 批量操作**:
- 批量插入：每批100-1000个向量
- 批量查询：每批10-50个查询

**2. 内存优化**:
- 使用 `on_disk=true` 降低内存占用
- 定期清理不用的 Collection

**3. 查询优化**:
- 合理设置 topK（通常5-20）
- 使用过滤条件减少搜索范围
- 按 document_id 过滤限定检索范围

**4. 监控指标**:
- 查询延迟（P50, P95, P99）
- 吞吐量（QPS）
- 内存使用率
- CPU 使用率
- 磁盘 I/O

## 5. Mock 模式开发优化

### 5.1 Mock 模式用途

- 本地开发无需部署 Ollama/Qdrant
- 快速验证接口和流程
- 单元测试不依赖外部服务
- CI/CD 环境无需 GPU

### 5.2 Mock 配置

```yaml
spring:
  profiles:
    active: mock
  main:
    allow-bean-definition-overriding: true

langchain4j:
  llm:
    provider: mock

embedding:
  provider: mock

vector:
  store:
    provider: mock
```

### 5.3 Mock 组件性能

| 组件 | 实现 | 特点 |
|------|------|------|
| MockLLMService | 固定回复 + 打字机效果 | 10ms/token |
| MockEmbeddingService | MD5 确定性向量 | ~1ms/文本 |
| MockVectorService | 内存 HashMap | ~0.1ms/检索 |

## 7. 面试准备

### 7.1 核心技术点

**1. 缓存设计**:
- **问题**: 如何设计多级缓存系统？
- **回答**: 
  - 本地缓存（Caffeine）：热点数据，毫秒级响应
  - Redis缓存：共享数据，跨实例访问
  - 数据库：持久化存储
  - 缓存策略：LRU淘汰，TTL过期，主动失效

**2. 批量处理优化**:
- **问题**: 如何优化大批量数据处理？
- **回答**:
  - API层面：使用批量接口减少网络往返
  - 数据库层面：批量插入减少事务开销
  - 并发处理：使用线程池并发执行
  - 内存控制：分批处理避免OOM

**3. 向量数据库优化**:
- **问题**: Qdrant 如何进行性能调优？
- **回答**:
  - 动态向量：同一 Collection 支持多维度，切换模型无需重建
  - 向量落盘：`on_disk=true` 降低内存占用
  - 距离度量：Cosine 适合语义检索
  - 分片副本：提升并发和可用性
  - 批量 upsert：减少网络开销

**4. 多提供商支持**:
- **问题**: 如何设计支持多个LLM提供商的系统？
- **回答**:
  - 抽象接口：定义统一的 `LLMService` 接口
  - 工厂模式：使用 `LLMServiceFactory` 管理不同实现
  - 配置驱动：通过配置文件切换提供商
  - 降级策略：主提供商失败时自动切换

### 7.2 系统设计问题

**问题1**: 如何设计一个高性能的RAG系统？

**回答要点**:
1. **架构设计**:
   - 分层架构：API层、服务层、数据层
   - 异步处理：文档索引异步化
   - 流式输出：提升用户体验

2. **性能优化**:
   - 缓存：多级缓存减少查询
   - 批量处理：减少API调用
   - 连接复用：Qdrant gRPC 连接复用
   - 并发控制：合理使用线程池

3. **可靠性保障**:
   - 重试机制：API调用失败重试
   - 熔断降级：服务不可用时降级
   - 监控告警：实时监控关键指标
   - 日志追踪：完整的请求链路

**问题2**: 缓存一致性如何保证？

**回答要点**:
1. **更新策略**:
   - Cache Aside：先更新数据库，再删除缓存
   - Write Through：同时更新数据库和缓存
   - Write Behind：先更新缓存，异步更新数据库

2. **失效策略**:
   - 主动失效：数据更新时主动删除缓存
   - 被动失效：设置TTL自动过期
   - 延迟双删：删除缓存后延迟再删一次

3. **分布式一致性**:
   - Redis Pub/Sub：通知其他实例失效缓存
   - 版本号：使用版本号检测数据变化
   - 最终一致性：接受短暂的不一致

### 7.3 代码实现细节

**1. 批量向量生成实现**:
```java
public List<float[]> batchGenerateEmbeddings(List<String> texts) {
    List<float[]> allEmbeddings = new ArrayList<>();
    
    for (int i = 0; i < texts.size(); i += batchSize) {
        int endIndex = Math.min(i + batchSize, texts.size());
        List<String> batch = texts.subList(i, endIndex);
        
        // 使用批量API
        List<float[]> batchEmbeddings = embeddingService.generateEmbeddings(batch);
        allEmbeddings.addAll(batchEmbeddings);
    }
    
    return allEmbeddings;
}
```
